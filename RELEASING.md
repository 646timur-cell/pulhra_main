# Ветки и выпуски PULHRA

## Ветки

| Ветка | Назначение | Автопубликация |
| --- | --- | --- |
| `main` | Проверенный код, база стабильных выпусков | Только CI, сайт не меняется |
| `develop` | Интеграция новой разработки | Экспериментальный сайт `/preview/` после успешной сборки |
| `feature/*`, `fix/*`, `chore/*` | Отдельная задача от `develop` | Только CI и скачиваемые артефакты |
| `release/*` | Необязательная подготовка кандидата | Только CI и артефакты |
| `firmware-builds` | Готовый сайт GitHub Pages | Управляется публикацией, не редактировать вручную |

Обычный путь: `feature/*` → PR в `develop` → проверка на FM-1 → PR в `main` → тег.
Срочный фикс: `fix/*` от `main` → PR в `main`, затем перенести исправление в `develop`.
После выпуска обновить `develop` из `main`. Не менять default branch: это `main`.

## Каналы и версии

- **Stable:** корень сайта, только теги `vX.Y.Z`, коммит тега должен входить в историю `main`.
- **Preview:** `/preview/`, текущий `develop`, версия вида `1.5.2-devabcdef0`. Stems и диагностическая сборка остаются здесь экспериментальными.
- **RC:** теги `vX.Y.Z-rcN`, GitHub prerelease, без изменения stable или preview сайта.
- **CI:** ветки задач и PR, только артефакты. Ручной запуск на `main` тоже не публикует сайт.

Теги — неизменяемые. Никогда не переносить тег и не заменять файлы существующего релиза.
Версия берётся из тега, а для preview — из `FELUCCA_VERSION` в `firmware/src/pulhra.c` и SHA.
Текущий упаковщик поддерживает одну цифру на компонент версии: например, `1.5.2`, но не `1.5.12`.
Расширение этого ограничения — отдельная задача; workflow отвергает неподдерживаемые теги до сборки.

## Первый стабильный выпуск

Исходный `7cf07fb0d9b9cf01805f5da6465414b25e085334` (1.5.1) проверен владельцем на FM-1.
Первый тег `v1.5.1` ставится после объединения настройки каналов в `main`: прошивочные
исходники относительно проверенного `7cf07fb` не меняются. В тег входят новый процесс выпуска,
документация и пометки каналов в установщике. Это позволяет выпустить стабильную базу уже
через новый workflow и сохранить комплект основной сборки с правильными контрольными суммами.

## Подготовка следующего выпуска

1. В начале следующего цикла изменить `FELUCCA_VERSION` в `develop` на следующую базовую версию.
2. Проверить CI и установить preview на FM-1. Проверить загрузку/сохранение, backup/restore,
   MIDI clock, USB audio и переключение банков. Записать результаты в PR.
3. При необходимости выпустить `v1.5.2-rc1` и проверить его артефакты на устройстве.
4. Объединить проверенную разработку в `main`. Убедиться, что CI прошёл.
5. Создать аннотированный тег на выбранном проверенном коммите:

   ```sh
   git switch main
   git pull --ff-only
   git tag -a v1.5.2 -m 'PULHRA 1.5.2'
   git push origin v1.5.2
   ```

6. Дождаться workflow `firmware`: GitHub Release и корень сайта должны показывать одну версию и SHA.
   Проверить `CHANNEL.json`, `SOURCE_COMMIT`, `SHA256SUMS` и ссылки установщика.

Архив `*-release.tar.gz` содержит пакет, app.bin, контрольные суммы и лицензии именно основной
сборки. Экспериментальные сборки не заменяют этот комплект. Логи доступны в Actions artifacts;
ветка `ci-logs` больше не обновляется. При повторном запуске уже опубликованного тега workflow
откажется заменять release assets. Если Release создан, но Pages push упал, восстановить Pages
из артефакта той же сборки через `tools/publish_site.py`, не пересобирая прошивку.

Откат: пользователю дать предыдущий GitHub Release. Stable сайт автоматически не понижается;
исправление выпускается новой версией. Публикация сохраняет другой канал и историю Pages-ветки.

## Настройки GitHub

Для `main` и `develop`: PR перед merge, обязательная успешная проверка `build` workflow `firmware`,
запрет force push и удаления. Для одного владельца обязательный чужой review не нужен.
Защита тегов `v*`: запрет изменения/удаления. GitHub Pages: `firmware-builds`, `/ (root)`.
Публикация сериализована; только publish job имеет `contents: write`. PR собираются с read-only token.
